# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могу:
    - Включать и выключать отопление в своих домах.
    - Устанавливать целевую температуру для системы отопления.
    - Обновлять параметры отопительной системы.
    - Просматривать текущую конфигурацию системы отопления.

- Система:
    - Обрабатывает команды включения и выключения отопления.
    - Сохраняет состояние (включено/выключено) и целевую температуру в базе данных.
    - Не поддерживает автоматическое управление температурой — логика поддержания температуры отсутствует (помечено как
      TODO в коде).
    - Не поддерживает сценарии или реактивные действия.
    - Не позволяет пользователям самостоятельно добавлять или удалять устройства — установка выполняется только
      специалистами вручную.

**Мониторинг температуры:**

- Пользователи могут
    - Получать текущую температуру для конкретной системы отопления.

- Система
    - Возвращает текущую температуру по запросу.
    - Не проводит периодическое обновление данных от датчиков.
    - Не хранит историю измерений.
    - Получает данные от датчиков по запросу от сервера к устройству (pull-модель).
    - Не поддерживает push-модель, WebSocket или асинхронные уведомления.
    - Работает синхронно: каждый запрос блокирует поток выполнения до получения ответа от устройства.

### 3. Определение доменов и границы контекстов

В текущей реализации есть два домена:

- Домен: Управление отоплением
    - Контекст: Включить/Отключить отопление
    - Контекст: Установить целевую температуру
    - Контекст: Предоставить текущее значение температуры
    - Контекст: Вернуть текущую конфигурацию отопительной системы

- Домен: Мониторинг температуры
    - Контекст: Получить температуру с датчика

### 4. Проблемы монолитного решения

- Ограниченная масштабируемость
    - Нельзя масштабировать только нагруженные части системы (например, наблюдение или управление светом).
    - При росте числа клиентов (умных домов) весь монолит становится узким местом.

- Зависимость компонентов
    - Все модули связаны жёстко: изменение в одной части (например, отоплении) может сломать другие (например,
      наблюдение).
    - Сложно изолировать и тестировать функциональность.

- Невозможность быстрой разработки новых модулей
    - Чтобы добавить новое направление (например, управление воротами), нужно менять монолит -> долгий цикл разработки и
      отката.

- Ограничения в развертывании и обновлениях
    - Любое изменение требует пересборки и полного перезапуска всего приложения.

- Невозможность самообслуживания пользователей
    - Архитектура не поддерживает регистрацию новых устройств пользователем.
    - Все подключения происходят вручную через выезд специалиста.

- Отсутствие поддержки асинхронного взаимодействия
    - Все вызовы синхронные -> невозможно быстро реагировать на события (например, сигнализация, поток с камеры,
      триггеры).

- Монотехнологичность
    - Вся система жёстко завязана на Java и Spring Boot -> невозможно использовать другие языки или технологические
      стеки для отдельных модулей (например, Python для аналитики видео).

- Монолитная база данных
    - Один экземпляр PostgreSQL обслуживает всё -> конфликт интересов в данных разных модулей (например, отопление и
      камеры).
    - Нет явной границы владения данными (data ownership).
